## Summary
[summary]: #summary

Rendering the frames of the main character sprite sheet to the screen subject to user input.

## Guide-level explanation
[guide-level-explanation]: #guide-level-explanation

A sprite sheet is an ordinary image divided into a grid of frames, each with the same dimensions (e.g., 32x32). 
Each row of the grid is an animation: playing it means showing the row’s frames one after another, then looping back to the first frame.
```
          frame 0   frame 1   frame 2   frame 3
        +---------+---------+---------+---------+
        |    o    |    o/   |    o    |   \o/   |
row 0   |   /|\   |   /|    |   /|\   |    |    |
        |   / \   |   / \   |   / \   |   / \   |
        +---------+---------+---------+---------+
        |    o/   |   \o/   |   \o    |         |
row 1   |   /|    |    |    |    |\   |  empty  |
        |   / \   |   / \   |   / \   |         |
        +---------+---------+---------+---------+
```

The way to think about it: an animation is just an frame that changes over time. Playing an animation is stepping through the frames of a row.
For example, suppose the animation of `row 0` should play while the player holds `W`:

1. We attach an animation component to the player entity. It keeps track of the state needed to render the animation: the current `frame`, a `timer`, and which `animation`.
If each animation is a variant of a sum type we can pattern match on a animation and get its metadata, such as the offset of the first frame or how many there are (4 for `row 0`).
2. A system reads the keyboard input each frame. While W is held, it selects the `row 0` animation, and sets `frame` to zero.
3. A second system ticks `timer`. Each time the timer fires, it increments `frame`, wrapping back to zero after the last frame.

## Reference-level explanation
[reference-level-explanation]: #reference-level-explanation

We keep track of all the essential rendering data in a single component `PlayerAnimationState`.
A new timer is only created when the animation changes, we can use `TimerMode::Repeating` to reset the timer without creating a new one.

```rust
#[derive(Component)]
pub struct PlayerAnimationState {
    /// Tracks the amount of time a frame has been on screen.
    timer: Timer,
    /// Which frame of the animation to draw to the screen.
    frame: usize,
    /// The animation that is playing.
    animation: PlayerAnimations,
}
```

A variant of the enum maps to a row or sequence of frames on the sprite sheet.

```rust
pub enum PlayerAnimations {
    Idling,
    Walking,
}
```

To keep repeating animations continuous during a frame drops we only advance the frame once for updates longer than the frame duration.
An alternative is to jump forward by the number of frames we missed, but we chose to advance only one frame to avoid missing frames.

```rust
impl PlayerAnimationState {
          /// Add the time elapsed since the last update, then move to the next frame if the timer finished.
          pub fn advance(&mut self, delta: Duration) { todo!() }
}
```

We considered only storing the absolute atlas index so we could copy it straight into the sprite. This seems simpler because it drops the mapping function, but it couples the animation logic to the atlas. Functions that used to care only about frames, like `advance`, now have to know where each animation starts and how long it is, because the simplest way to wrap the atlas index is `((index - start) mod frame_count) + start`.

We instead store the local frame number of the current animation, and convert it to an atlas index independently. This decouples the animation logic from the atlas.

```rust

```
